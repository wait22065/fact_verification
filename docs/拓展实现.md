# EXTENDED_PIPELINE 拓展实现分析

## 一、概览

`EXTENDED_PIPELINE` 是本项目在标准 FEVER 单跳验证之外的拓展实验，核心特征是：

- **换用 HoVer 多跳数据集**，替代 FEVER 数据集
- **多跳实时检索**：用 LLM 提取关键词 → Wikipedia API 搜索多个页面 → Sentence-BERT 语义筛句
- **LLM-as-Judge**：让大模型充当"裁判"，仅凭检索到的证据做一致性判断

---

## 二、数据集：HoVer

### 2.1 来源与格式

| 属性 | 说明 |
|------|------|
| 文件路径 | `data/cache/hover_dev.json` |
| 原始格式 | JSON 数组，每条含 `uid`、`claim`、`label` 字段 |
| 原始标签 | `SUPPORTED` / `NOT_SUPPORTED` |
| 转换后标签 | `SUPPORTS` / `REFUTES`（项目统一标签体系）|

标签映射逻辑（`data_loader.py:30-31`）：

```python
label = "SUPPORTS" if original_label == "SUPPORTED" else "REFUTES"
```

> **注意**：HoVer 只有两类标签，不存在 `NOT ENOUGH INFO`，这与 FEVER 的三分类不同。

### 2.2 HoVer 数据集的特点

HoVer（Hop Verification）专为**多跳事实验证**设计，区别于 FEVER 的核心在于：

- **单条 claim 需要跨多个 Wikipedia 页面**才能验证，通常需要 2-4 跳
- 声明中包含多个相互关联的实体，验证时需要先找到实体 A，再通过 A 跳转找到 B，最终综合判断
- 官方规模：训练集约 18k，Dev 集约 4k，全部来自人工标注

**示例**：
> "The film that was released in the same year as X-Men was directed by a Canadian director."

要验证这条声明，需要：
1. 查 X-Men 的上映年份
2. 查同年上映的另一部电影
3. 查该导演的国籍

这三步形成了一条"证据链"，单跳检索无法完成。

## 三、什么是多跳事实验证

### 3.1 单跳 vs 多跳

| 维度 | 单跳（FEVER） | 多跳（HoVer） |
|------|--------------|--------------|
| 验证依据 | 单篇 Wikipedia 页面中的一两句话 | 需要跨多个页面，综合多条证据 |
| 推理复杂度 | 直接比对即可 | 需要串联多条事实形成逻辑链 |
| 典型声明 | "X was born in Y" | "The director of film A won an award that was also won by person B" |
| 检索策略 | 单次搜索 | 需要迭代检索或同时检索多个实体 |

### 3.2 本项目的"多跳"简化实现

严格意义上，多跳需要迭代式检索（第一跳结果引导第二跳查询）。本项目采用的是一种**实用化简化**：

1. 用 LLM 一次性从 claim 中提取核心关键词（可能涵盖多个实体）
2. 用该关键词同时检索多个 Wikipedia 页面（`results=3`）
3. 聚合所有页面的句子，用 Sentence-BERT 统一筛选

虽然不是严格意义上的迭代多跳，但通过"一次检索多页面"的方式，让模型有机会看到不同实体的信息，再由 LLM 综合推断。

## 五、检索实现详解

入口函数：`retrieve_evidence_pipeline(claim, entity_query, top_k_sentences=3)`（`retriever.py:642`）

### 5.1 Step 1：LLM 关键词提取（verifier.py:109-116）

```python
kw_prompt = (
    f"Return 1-2 core keywords from this claim for Wikipedia search: "
    f"'{claim}'. Reply ONLY with the keywords, separated by space."
)
extracted = self.client.call_api(kw_prompt)
# 超过6个词视为失败，直接用原始 claim
if extracted and len(extracted.split()) <= 6:
    search_query = extracted.strip("'\"., ")
```

- 调用一次 DeepSeek API，让模型提取关键词
- 防御性判断：超过 6 个词说明模型返回了整句而非关键词，回退到原始 claim

### 5.2 Step 2：Wikipedia API 多页面搜索（retriever.py:648-663）

```python
search_results = wikipedia.search(entity_query, results=3)   # 搜出 3 个候选标题
for title in search_results:
    content = wikipedia.page(title, auto_suggest=False).content
    sentences = nltk.sent_tokenize(content)
    clean_sentences = [s.strip() for s in sentences if len(s) > 20][:30]
    all_sentences.extend(clean_sentences)
```

- 每个 claim 最多拉取 3 个 Wikipedia 页面
- 每页最多取前 30 句（过滤掉长度 < 20 字符的短句）
- 汇总后最多有 90 个候选句子

### 5.3 Step 3：Sentence-BERT 语义筛句（retriever.py:665-673）

```python
model             = get_st_model()                           # 单例，懒加载
claim_embedding   = model.encode(claim, convert_to_tensor=True)
corpus_embeddings = model.encode(all_sentences, convert_to_tensor=True)

cos_scores  = util.cos_sim(claim_embedding, corpus_embeddings)[0]
top_results = torch.topk(cos_scores, k=min(top_k_sentences, len(all_sentences)))

evidence_chain = [all_sentences[idx] for idx in top_results[1]]
return "\n".join([f"• {s}" for s in evidence_chain])
```

| 参数 | 说明 |
|------|------|
| 模型 | `all-MiniLM-L6-v2`（80MB，384维，CPU友好） |
| 相似度 | 余弦相似度（cosine similarity） |
| 最终输出句子数 | `top_k_sentences=3`（默认值） |
| 输出格式 | `• 句子1\n• 句子2\n• 句子3`（bullet 列表） |

**与 RAG_BM25 的关键区别**：

| 维度 | RAG_BM25 | EXTENDED_PIPELINE |
|------|----------|-------------------|
| 数据来源 | 本地 FEVER wiki dump | 实时 Wikipedia API |
| 检索第一阶段 | BM25（词频匹配） | Wikipedia 全文搜索引擎 |
| 关键词 | 不提取，用完整 claim | LLM 提取 1-2 个关键词 |
| 句子池规模 | 每次 BM25 召回5篇×50句=250句候选 | 3篇×30句=90句候选 |
| 适用场景 | 离线，不需要网络 | 在线，需要网络和代理 |

## 六、一致性判断实现（LLM-as-Judge）

### 6.1 Prompt 设计（prompt_builder.py:155-172）

```python
def build_llm_judge_prompt(claim, evidence):
    prompt = f"""You are an objective LLM-as-a-Judge evaluating a fact-checking task.

Is the claim consistent with the evidence?

Claim: {claim}

Evidence:
{evidence}

Instructions: 
Based ONLY on the evidence above, determine if the claim is supported or refuted.
Please output your final conclusion on a new line exactly as follows:
Final Label: SUPPORTS 或 REFUTES 或 NOT ENOUGH INFO

Analysis:"""
    return prompt
```

**设计要点**：

1. **角色定位**：明确告诉模型它是"裁判"（Judge），不是知识库
2. **严格限定证据范围**：`Based ONLY on the evidence above`，防止模型使用内置知识
3. **固定输出格式**：`Final Label: XXX`，方便正则解析
4. **开放分析区域**：`Analysis:` 后让模型自由推理，最后一行给结论

### 6.2 响应解析（prompt_builder.py:178-203）

`parse_model_response()` 采用多级容错策略：

```
优先：正则匹配 "Final Label: SUPPORTS/REFUTES/NOT ENOUGH INFO"
      ↓ 失败
次级：在全文中找最后出现的关键词（rfind），取位置最靠后的标签
      ↓ 失败
兜底：宽松匹配 SUPPORT/REFUTE，排除 NOT SUPPORTS 等干扰词
      ↓ 全部失败
返回 None，该条记录跳过不纳入评估
```

### 6.3 与其他模式的判断方式对比

| 模式 | 判断方式 | 使用证据 |
|------|----------|---------|
| BASELINE | LLM 直接内置知识 | 无 |
| RAG | LLM 看证据简单比对 | Wikipedia 摘要 |
| COT | LLM 思维链推理 | 无（纯内置知识） |
| RAG_COT | LLM 看证据 + 思维链 | Wikipedia 摘要 |
| **EXTENDED_PIPELINE** | **LLM-as-Judge，严格基于证据** | **多页面语义筛句** |

LLM-as-Judge 范式的核心优势是：通过 Prompt 约束，让模型扮演"客观第三方评判者"，而不是直接回答问题，理论上减少了模型内置知识的干扰。

## 七、评估指标

`calculate_metrics()`（`evaluator.py:14`）计算以下指标：

| 指标 | 说明 |
|------|------|
| Accuracy | 总体正确率 |
| Macro Precision/Recall/F1 | 各类等权平均（适合类别不均衡场景） |
| Weighted F1 | 按样本数加权平均 |
| 幻觉率 | 真实为 NEI 但预测为 SUPPORTS/REFUTES 的比例 |
| 混淆矩阵 | 3×3，行为真实标签，列为预测标签 |

> **HoVer 场景特殊说明**：由于 HoVer 只有 SUPPORTS/REFUTES 两类，没有 NOT ENOUGH INFO 样本，**幻觉率恒为 0.0**，该指标在此模式下无参考意义。

## 九、关键限制与潜在改进

### 9.1 现有实现的局限

1. **非严格多跳**：只做了"单次多页面检索"，没有实现迭代式跳转（找到第一跳结果后再发起第二跳查询）
2. **关键词提取质量**：依赖 LLM 提取的 1-2 个词，多实体 claim 可能只覆盖部分实体
3. **网络依赖**：实时调用 Wikipedia API，需要代理（`http://127.0.0.1:17890`），不适合离线运行
4. **每次检索调用 API 两次**（关键词提取 + 最终判断），成本是其他模式的两倍
5. **HoVer 标签只有两类**，不支持 NOT ENOUGH INFO，与 FEVER 评估体系不完全兼容

### 9.2 潜在改进方向

| 改进点 | 思路 |
|--------|------|
| 真正多跳检索 | 解析 claim 中所有实体，迭代检索每个实体页面，逐步构建证据链 |
| 混合检索 | 结合 BM25 召回（覆盖率高）+ SBERT 精排（相关性高） |
| 专用 Reranker | 用 cross-encoder 模型对候选句子重排，精度高于 bi-encoder |
| 结构化证据 | 解析 Wikipedia 信息框（Infobox），提供结构化事实而非自由文本 |
