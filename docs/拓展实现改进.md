# EXTENDED_PIPELINE 改进方案文档

## 一、概述

本文档描述针对 `EXTENDED_PIPELINE` 模式的完整改进演进过程，记录从初版单跳本地检索出发、历经五轮系统性尝试的全部过程，包括成功的改进、无效的探索及其失败原因，以及最终实现的优缺点与可改进方向。

所有改进以布尔开关或配置参数写入 `src/config.py`，支持独立启用或任意组合，便于进行**消融实验**（Ablation Study），定量对比每项改进的贡献。

当前最终配置：

```python
USE_MULTI_HOP     = True   # IRCoT 多跳检索
MAX_HOP_ROUNDS    = 3      # 最大跳数上限
USE_CROSS_ENCODER = True   # Cross-Encoder 精排
USE_LLM_JUDGE     = False  # LLM Judge 二次核验（净负效果，已关闭）
RETRIEVAL_MODE    = "BM25" # 第一阶段检索（Dense/Hybrid 均劣于 BM25）
```

所有开关仅对 `EXPERIMENT_MODE = "EXTENDED_PIPELINE"` 生效。

---

## 二、演进概述

### 2.1 起点：单跳本地检索

初版 EXTENDED_PIPELINE 采用本地 dump 单次检索：一次性搜索 claim 对应页面，将候选句子汇总排序后交给 LLM 判断。此前曾尝试实时 Wikipedia API，但因 API 空响应（`json.JSONDecodeError`）、实体歧义消解失控（同名词条命中错误页面）、结果无法复现三类系统性问题而废弃，改为查询本地 dump（与 FEVER wiki-pages dump 格式相同），作为所有后续实验的基础。

单跳方案在 HoVer 多跳声明上存在结构性缺陷：验证 "The company that produced film X also produced film Y" 需要先找 film X 的制作公司（跳1），再查该公司是否制作了 film Y（跳2），并行搜索两者得到的是两堆独立信息，无法建立实体间关联。

### 2.2 五轮改进一览

以下汇总所有尝试在 **seed=42，n=50** 基准下的效果：

| 阶段 | 核心变化 | Accuracy | Macro F1 | SUPPORTS 召回 | REFUTES 召回 | 效果 |
|------|---------|---------|---------|-------------|------------|------|
| 起点：单跳 + SBERT | 单次本地检索，无多跳 | 50% | 0.490 | 0.321 | 0.727 | 基线 |
| 尝试一：+多跳 IRCoT | 迭代链式检索，每跳一步推理 | 60% | 0.597 | 0.464 | 0.773 | **+10% ✅** |
| 尝试二：+Cross-Encoder | 多跳基础上加 CE 精排 | 66% | 0.657 | 0.500 | 0.864 | **+6% ✅** |
| 尝试三：Dense 替换 BM25 | FAISS 向量检索替换第一阶段 | 62% | 0.616 | 0.464 | 0.818 | −4% ❌ |
| 尝试三：BM25+Dense 混合 | 并集候选再排序 | 66% | 0.647 | 0.571 | 0.773 | 一致 |
| 尝试四：逐子句校验（三态标签） | 强制拆解子句 + 三态规则 | 64% | — | 0.857 | 0.364 | −2% ❌ |
| 尝试四：逐子句校验（显式规则） | few-shot + 任意矛盾→REFUTES | 64% | — | 0.393 | 0.955 | −2% ❌ |
| 尝试四：逐子句校验（纯 few-shot） | 仅用示例隐式传递逻辑 | 62% | — | 0.393 | 0.909 | −4% ❌ |
| 尝试五：LLM Judge 二次核验 | 基础核验后再加一轮 LLM 审核 | 62% | 0.616 | 0.464 | 0.818 | −4% ❌ |

**当前最佳组合**（尝试一 + 尝试二）：Accuracy **66%**，Macro F1 **0.657**。

### 2.3 演进规律

从实时 API 切换到本地检索是整个改进的前提条件，消除了网络不稳定和实体歧义两类噪声，使后续消融实验可比较。

在本地检索基础上，多跳 IRCoT（尝试一）和 Cross-Encoder 精排（尝试二）是两个真正有效的改进，合计提升 16%。此后三轮尝试（Dense 检索、逐子句校验、LLM Judge）均未能突破 66% 的瓶颈，失败原因高度一致：**检索覆盖率不足时，任何判断层或检索层的额外处理都倾向于放大同侧误差，而非纠正错误**——无论是偏向 SUPPORTS 还是偏向 REFUTES，结果都是准确率下降。

## 三、尝试一：多跳 IRCoT 检索

### 3.1 背景与动机

单跳方案对 HoVer 的链式声明完全失效（见 2.1 节）。最初的多跳方案采用"先用一次 LLM 生成完整检索计划，再按计划逐跳执行"的方式，实验发现两个根本缺陷：

1. **规划阶段无检索依据**：LLM 只能凭参数记忆臆测需要哪些页面，记忆有误则整条计划偏轨。
2. **解析脆弱**：依赖从整段规划文本中提取 `First search:` 关键行，LLM 输出 Markdown 加粗格式 `**First search:**` 时静默失败（`startswith("first search:")` 不匹配 `**first search:**`）。

参考 **IRCoT**（Interleaving Retrieval with Chain-of-Thought，Trivedi et al., ACL 2023）的思想，改为每生成一步推理就立即触发一次检索，将检索结果追加到上下文后再继续：

```
Thought1: [分析 claim，推断第一步要找什么] → Search: 词条A
Observation1: [词条A 的检索结果]
Thought2: [结合 Observation1 推断下一步] → Search: 词条B
...
ThoughtN: [证据已充足] → Done
```

### 3.2 实现方案

**本地检索接口**：每跳调用 `retrieve_evidence_from_dump(query)`，流程为：

```
BM25 文档检索（query → Top-N 篇文档）→ 收集候选句子 → SBERT 语义排序 → Top-K 句
```

**IRCoT 循环（`verifier.py`）**：

```
hop 0: LLM 看 claim → 输出 "Thought: [分析] | Search: [词条A]"
       → 解析词条 → 本地检索
hop 1: LLM 看 claim + Observation0 → 输出 "Thought: [...] | Search: [词条B]"
       → 本地检索
...
hop N: LLM 看 claim + 所有 Observation → 输出 "Thought: [...] | Done" → 退出
```

**去重与停止机制**：`searched_titles` 集合（大小写归一化）记录已查词条，重复词条代码层直接跳过，同时在 prompt 中列出已查词条告知 LLM；`MAX_HOP_ROUNDS` 硬性上限防止循环失控；LLM 判断证据充足时输出 `Done` 主动提前退出。

**Jaccard 换方向约束**：检测最近两跳查询的词袋相似度（Jaccard ≥ 0.5），若卡死在同一实体则在 prompt 中强制要求切换方向，避免三跳浪费在同一文档的查询变体上。

**LLM 调用次数**：

| 方案 | 调用次数 |
|------|---------|
| 原始单跳 | 1 次判断 |
| IRCoT（满 3 跳） | 3 次推理+查询 + 1 次判断 = 4 次 |
| IRCoT（LLM 2 跳 Done） | 2 次推理+查询 + 1 次判断 = 3 次 |

**开发过程中修复的问题**

| 问题 | 现象 | 修复方案 |
|------|------|---------|
| LLM 零跳直接 Done | 50 条数据中 22 条"No evidence retrieved"，hop0 允许 Done，LLM 凭空判断"证据充足"直接终止 | IRCoT 格式要求 hop0 输出 `Search: xxx`，从格式上杜绝零跳 |
| 反复检索同一词条 | 修复零跳后"No evidence"反升至 32/50，三跳全搜同一词条变体 | 双重去重：代码层硬拦截 + prompt 层软约束 |
| Markdown 解析失败 | `**First search:**` 无法被 `startswith("first search:")` 匹配 | 改用 IRCoT 固定格式，代码按 `Action: Search[...]` 正则解析，消除 Markdown 依赖 |

### 3.3 实验结果

以下对比在 seed=42, n=50 下，单跳基线与启用 IRCoT 多跳的效果（均不启用 CE 和 LLM Judge）：

| 指标 | 单跳基线 | +IRCoT 多跳 | 变化 |
|------|---------|-----------|------|
| Accuracy | 50.0% | **60.0%** | +10.0% |
| Macro F1 | 0.490 | 0.597 | +10.7% |
| SUPPORTS F1 | 0.419 | 0.565 | +14.6% |
| SUPPORTS Recall | 0.321 | 0.464 | +14.3% |
| REFUTES F1 | 0.561 | 0.630 | +6.9% |
| REFUTES Recall | 0.727 | 0.773 | +4.6% |

IRCoT 在所有指标上均有提升，SUPPORTS 类改善尤为显著，验证了链式推理检索对 HoVer 多跳声明的有效性。

**仍存在的主要错误模式**

| 错误类型 | 典型表现 | 根本原因 |
|---------|---------|---------|
| IRCoT 卡死同一词条 | 三跳全是同一文档的查询变体（`Forever Strong film / cast / cast list`）| LLM 缺乏换角度约束 |
| BM25 实体消歧错误 | 搜 `She's So Huge song` 命中 Halo 2 游戏曲目而非目标乐队 | BM25 对模糊词条召回精度不足 |
| 证据链最后一环缺失 | 找到两个实体但无直接证据建立关联 | 多跳未生成桥接查询 |
| 数值推理失败 | 证据含生年和年龄差，LLM 未做显式算术 | 判断 prompt 未要求 LLM 显式计算 |

### 3.4 总结

多跳 IRCoT 是五轮改进中效果最显著的一项（+10%），其关键贡献在于推理与证据实时对齐（每步 Thought 基于真实检索结果）、格式化输出消除 Markdown 解析问题、动态适应 claim 复杂度。主要瓶颈在于 BM25 检索层的实体消歧能力和 SBERT bi-encoder 架构对细粒度查询-文档交互不敏感，由尝试二（Cross-Encoder）进一步改进。

## 四、尝试二：Cross-Encoder 精排

### 4.1 背景与动机

本地检索的 SBERT 是 bi-encoder：claim 和候选句子**独立编码**，用余弦相似度排序，存在两类系统性偏差：

1. **表面共现偏差**：优先选取与 claim 字面重叠高的句子，而非逻辑上最能回答问题的句子。Christopher Kelly 案例中，"Christopher Kelly the novelist"因同名共现度高被 SBERT 排前，真正需要的"journalist for Texas Monthly"被排后。
2. **单向编码盲区**：候选句子编码时看不到 claim，无法理解 claim 的隐含需求（"需要年龄数据"、"需要桥接两实体的关系句"等），只能做静态语义相似度匹配。

### 4.2 实现方案

在 SBERT 排序之后插入 Cross-Encoder 精排阶段：

```
本地检索流程:
  BM25 文档检索 → 候选句子池 → SBERT 粗排（top-20）→ Cross-Encoder 精排 → top-K
```

Cross-Encoder 将 `(claim, 候选句子)` **联合输入**同一模型，交叉注意力层在评分时同时看到两者：

```python
ce_model  = get_ce_model()
ce_scores = ce_model.predict([[claim, s] for s in candidates])
ranked    = sorted(zip(ce_scores, candidates), reverse=True)
```

模型为 `cross-encoder/ms-marco-MiniLM-L-6-v2`（约 80MB，CPU 可运行），以单例模式懒加载，首次调用时自动从 HuggingFace 下载。

### 4.3 实验结果

以下为同一多跳配置（seed=42，n=50）下，不启用 CE 与启用 CE 的对比：

| 指标 | 多跳无CE | 多跳+CE | 变化 |
|------|---------|--------|------|
| Accuracy | 60% | **66%** | +6% |
| Macro F1 | 0.597 | **0.657** | +6.0% |
| SUPPORTS Recall | 0.464 | **0.500** | +3.6% |
| SUPPORTS F1 | 0.565 | **0.622** | +5.7% |
| REFUTES Recall | 0.773 | **0.864** | **+9.1%** |
| REFUTES F1 | 0.630 | **0.691** | +6.1% |

混淆矩阵：1 个 SUPPORTS→REFUTES 误判被纠正，2 个 REFUTES→SUPPORTS 误判被纠正，总正确数从 30 升至 33（+3）。

**典型成功案例**

| 案例 | 无CE | 有CE | CE 生效机制 |
|------|------|------|-----------|
| Christopher Kelly / Texas Monthly（真实 SUPPORTS）| REFUTES ✗ | SUPPORTS ✓ | 联合编码识别"journalist"属性对应，将"journalist for Texas Monthly"句置顶 |
| Estelle Getty / Bea Arthur 生年（真实 SUPPORTS）| REFUTES ✗ | SUPPORTS ✓ | 识别"生年"需求，将含出生年和年龄差的句子置顶，激活 LLM 数值推理 |
| B.V. Radha / Navakoti Narayana（真实 SUPPORTS）| REFUTES ✗ | SUPPORTS ✓ | 找到"based on the life of Purandara Dasa"桥接句，完成两实体关联 |

**典型失败案例**

Celtic FC（真实 REFUTES）：CE 精排同时召回了"founded in 1887"和"Glasgow, Scotland"，但 LLM 注意力被最显眼的数字（成立年份）吸引，忽略了"English vs Scotland"矛盾，输出 SUPPORTS（错误）。**根本原因是 LLM 判断层的"部分支持→整体认可"问题，不是 CE 检索失误。**

**仍存在的失败模式**

| 失败类型 | 根本原因 |
|---------|---------|
| LLM 忽略多子句中的矛盾子句 | CE 已召回正确证据，但 LLM 选择性确认，需逐子句逐一验证（见尝试四） |
| BM25 实体消歧错误（CE 无法弥补） | CE 只能在 BM25 已召回的候选内精排，BM25 阶段错误无从纠正 |
| dump 词条内容不足 | 部分词条本身只有基本描述，换方向检索仍返回同样内容 |
| BM25 名称歧义 | `Street Dogs` 命中街头犬科普页，三跳全返回无关内容 |

### 4.4 总结

Cross-Encoder 精排在多跳基础上带来了稳定提升（+6%），其核心优势在于联合编码能捕捉 claim 隐含需求与候选句子之间的细粒度语义交互，对多跳声明中"语义隐含关联句"的识别效果尤为显著。值得注意的是，CE 在本次实验中对 REFUTES 类的提升（召回 +9.1%）更为明显，而非此前部分实验中体现的对 SUPPORTS 类的大幅改善——这提示 CE 的边际效益受到当次 IRCoT 检索质量的影响，存在一定的随机性。

受限于 BM25 召回阶段：CE 只能在 BM25 已召回的文档候选内精排，BM25 阶段的实体消歧错误 CE 无法纠正，这驱动了尝试三（Dense 检索）的探索。

## 五、尝试三：Dense 稠密向量检索

### 5.1 背景与动机

尝试二的失败案例分析揭示了 BM25 的核心缺陷：IRCoT 生成的查询词与 Wikipedia 词条词汇不一致时（同义词、查询变体），BM25 得分为零，正确文章无法召回。FAISS + Dense Embedding 通过将查询和文档编码到同一语义空间来解决词汇缺口，理论上能找到"语义相近但词汇不同"的文档。

### 5.2 实现方案

**索引构建**：与 BM25 使用相同的页面集合（从 `hover_dev.json` 的 `supporting_facts` 字段提取目标页面），区别在于：

- BM25：对文档全文分词，构建 BM25Okapi 词频索引（`bm25.pkl`）
- Dense：用 SBERT（`all-MiniLM-L6-v2`）对文档全文编码，归一化后构建 FAISS `IndexFlatIP`，索引文件为 `faiss_index.bin`

两种索引的 `doc_ids.pkl` 和 `sentences.pkl` 格式完全相同，可复用句子级数据。

**检索流程**（通过 `config.py` 中 `RETRIEVAL_MODE` 切换）：

- `"BM25"`：BM25 文档检索 → SBERT 句子排序 → CE 精排
- `"DENSE"`：FAISS 近邻搜索 → SBERT 句子排序 → CE 精排
- `"HYBRID"`：BM25 和 FAISS 各取 top-N，取并集 → SBERT 句子排序 → CE 精排（BM25 结果排前，Dense 补充去重后的新文档）

### 5.3 实验结果

三种模式在相同配置（IRCoT 多跳 + CE，seed=42，n=50）下的对比：

| 检索模式 | Accuracy | Macro F1 | SUPPORTS 召回 | REFUTES 召回 |
|---------|---------|---------|-------------|------------|
| BM25（基准） | **66%** | **0.657** | **0.500** | 0.864 |
| DENSE | 62% | 0.616 | 0.464 | **0.818** |
| HYBRID（并集） | 66% | 0.647 | 0.571 | 0.773 |

**典型案例对比（Christopher Kelly，真实 SUPPORTS）**

| 模式 | Hop 1 返回 | 最终判断 |
|------|---------|---------|
| BM25 | `Kelly, an openly gay man, is a film critic and journalist for Texas Monthly.` | **SUPPORTS ✓** |
| DENSE | `Christopher Edward 'Chris' Hansen... is an American television journalist.` | REFUTES ✗ |

### 5.4 失败原因分析

**Dense 劣于 BM25 的核心原因：IRCoT 查询恰好是 BM25 的强项**

IRCoT 生成的 hop 查询几乎都是**命名实体查询**（人名、地名、组织名），例如 `Search[Christopher Kelly journalist]`、`Search[Lake Kanasatka elevation]`。对这类查询：

- BM25：精确关键词匹配，对词条中出现目标人名的文章赋予高权重，直接命中目标
- Dense（all-MiniLM-L6-v2）：将查询编码为"某位记者"的语义向量，与其他著名记者的文章在语义空间距离反而更近，返回名字不同但职业相似的错误文章

**根本反直觉之处**：Dense Retrieval 擅长解决语义缺口（"music group" 能找到 "band" 相关文章），但对专有名词的精确匹配能力反不如 BM25——专有名词在语义空间中没有规律，"Christopher Kelly"和"Chris Hansen"的语义向量距离比词频距离近得多。

**HYBRID 未达预期**：BM25 对 IRCoT 的命名实体查询覆盖已相当充分，Dense 补充的文档多为"主题相关但实体不同"的噪声，并集后有效文档占比下降，SBERT 排序质量下滑。

**文档级编码截断（次要因素）**：`all-MiniLM-L6-v2` 最大输入 256 token（约 150-200 英文词），Wikipedia 文章通常超过此限制，文章后半段的具体属性句可能被截断，文档级向量无法反映查询需要的信息。

### 5.5 总结

对于本项目的 HoVer 多跳验证任务，**BM25 已足够，Dense Retrieval 引入的问题多于解决的问题**：IRCoT 的 hop 查询本质上是命名实体查找，正是 BM25 精确匹配的强项；Dense 在语义空间对专有名词的区分能力不如词频统计；HYBRID 并集引入的噪声多于有效补充。

`RETRIEVAL_MODE` 保留 `"DENSE"` 和 `"HYBRID"` 选项供消融实验复现，默认值还原为 `"BM25"`。Dense Retrieval 在**词汇缺口更严重的场景**（描述性查询、同义词多、专有名词少）下更具优势，在本任务中不适用。

## 六、尝试四：LLM 逐子句校验

### 6.1 背景与动机

尝试二的 Celtic FC 失败案例揭示了 LLM 判断层的"部分支持→整体认可"问题：CE 同时检索到"founded in 1887"和"Glasgow, Scotland"，但 LLM 注意力被最显眼的数字（成立年份）吸引，忽略了"English"与"Scotland"的直接矛盾，最终输出 SUPPORTS（错误）。

改进思路是：**在判断 prompt 中要求 LLM 先拆解声明，再逐子句核查证据，最后综合给出结论**，以解决整体判断时的选择性确认问题。

### 6.2 三种 Prompt 设计方案

**方案一：三态标签（CONFIRMED / CONTRADICTED / UNSUPPORTED）**

强制 LLM 将声明拆解为 2~4 个可验证子事实，对每个子事实标注三种状态之一，最后按规则决策：

- 任意子事实 CONTRADICTED → REFUTES
- 否则（全部 CONFIRMED 或 UNSUPPORTED）→ SUPPORTS
- UNSUPPORTED 单独不触发 REFUTES，防止检索缺失误伤 SUPPORTS 样本

**方案二：few-shot + 显式规则**

用两个 few-shot 例子（Lake Kanasatka 展示 SUPPORTS，Celtic FC 展示 REFUTES）教会模型核查全部属性，同时保留"任意属性矛盾即为 REFUTES"的显式指令。

**方案三：纯 few-shot，无显式规则**

保留两个 few-shot 例子，删除所有 if-then 规则句，仅在 few-shot 示例中隐式传递"大部分确认但有一个属性矛盾→REFUTES"的判断逻辑，让模型自然推理。

### 6.3 实验结果

所有方案均在 seed=42, n=50, IRCoT + CE 配置下运行：

| 方案 | Accuracy | SUPPORTS 召回 | REFUTES 召回 | 主要偏差方向 |
|------|---------|-------------|------------|------------|
| 基准（原 prompt，无结构） | **72%** | 71% | 73% | 无明显偏向 |
| 三态标签 | 64% | **86%** | 36% | 严重偏 SUPPORTS |
| few-shot + 显式规则 | 64% | 39% | **95%** | 严重偏 REFUTES |
| 纯 few-shot | 62% | 39% | 91% | 偏 REFUTES |

三种方案准确率均下降至 62~64%，且偏差方向不稳定。

**三态标签版失败分析（REFUTES→SUPPORTS 误判 14 条）**

| 失败类型 | 数量 | 原因 |
|---------|-----|------|
| BM25 完全检索失败（三跳全返回无关文章） | 7 | 全部子句 UNSUPPORTED → 规则强制 SUPPORTS |
| 部分检索成功但关键错误事实未被召回 | 5 | 1~2 子句 CONFIRMED + 其余 UNSUPPORTED → 同上 |
| 证据不兼容但模型标注为 UNSUPPORTED | 1 | "fishing village"应判 CONTRADICTED，被标为 UNSUPPORTED |
| 复杂多跳指代误读 | 1 | LLM 将代词回指解析错误 |

只有 1 条是 prompt 层面可修复的；其余 13 条均为检索层失败，无论如何设计判断规则都无法纠正。

### 6.4 失败原因分析

**（1）显式决策规则在 LLM 中会被过度触发**

只要 prompt 中出现"如果 X 则判断为 Y"的句式，模型就会将该路径踩死。三态标签的`UNSUPPORTED→SUPPORTS`让 13/14 的 REFUTES 被误判为 SUPPORTS；Celtic FC 例子里"nationality is wrong → REFUTES"则导致 16/28 的 SUPPORTS 被误判为 REFUTES。规则越显式，偏差越严重。

**（2）二分类 + 检索不完整 = 无解的两难**

HoVer 数据集只有 SUPPORTS / REFUTES，没有 NOT ENOUGH INFO。当检索失败时，模型无论选哪边都是在猜测——结构化 prompt 会**固化猜测方向**，使误差集中在同一侧。原有简单 prompt（无结构、无规则）在整体判断中能部分利用模型内置知识兜底，维持了相对均衡的 72%。

**（3）few-shot 的 Celtic FC 示例引入了强偏置**

Celtic FC 例子展示"大部分事实确认但一个属性矛盾→REFUTES"，模型将这一模式过度泛化：当检索结果中有任何不一致（包括无关内容、格式不匹配）都倾向于输出 REFUTES，无法区分"明确矛盾"和"证据不足"。

### 6.5 总结

**逐子句验证的思路本身合理**，能够解决 Celtic FC 类"LLM 注意力偏移"问题。但在当前检索质量下，该方法放大了检索层的缺陷：结构化规则成为系统性偏差的来源，无论规则设计偏向哪侧都会大幅降低另一侧的召回率。

相关代码（`build_extended_pipeline_judge_prompt`）已注释保留在 `src/prompt_builder.py` 中，便于后续复现。**检索层覆盖率显著提升后，逐子句校验才有意义上线。**

## 七、尝试五：LLM Judge 二次核验

### 7.1 背景与动机

基础核验由 LLM 一次性完成"看证据→给标签"，如果检索证据质量差或存在误导性句子，LLM 可能在第一次就给出错误标签，且没有机会自我纠错。改进思路是增加一轮独立视角的审核：由独立 Judge 看到初判结果后对照证据重新审核，仅在证据明确反驳初判时才翻转。

### 7.2 实现方案

在基础核验之后额外增加一轮 Judge 审核：

```
检索证据 → [Step 1] LLM 基础核验 → 初步标签
                                      ↓（USE_LLM_JUDGE=True）
                        [Step 2] LLM Judge 二次核验 → 最终标签
```

Judge prompt（`build_judge_review_prompt`）核心指令：

```
Strictly review the initial verdict against the evidence above.
- If the evidence contains numerical or directional relationships, verify the reasoning before deciding.
- Correct the verdict only if the evidence clearly contradicts it.
Output ONLY 'SUPPORTS' or 'REFUTES'.
```

设计意图保守：只有证据**明确反驳**初判时才翻转，否则维持原判。

| USE_LLM_JUDGE | 额外 LLM 调用 | 总调用（不含多跳） |
|---|---|---|
| False（默认） | 0 次 | 1 次基础核验 |
| True | +1 次 | 2 次（核验 + 审核）|

### 7.3 实验结果

对应结果文件：
- 无二次核验：`verification_results_extended_pipeline_multihop_ce_20260529_221616.json`
- 有二次核验：`verification_results_extended_pipeline_multihop_ce_judge_20260529_222621.json`

| 指标 | 无二次核验 | 有二次核验 | 变化 |
|------|-----------|-----------|------|
| Accuracy | **0.66** | **0.62** | −0.04 |
| Macro F1 | 0.659 | 0.616 | −0.043 |
| SUPPORTS Recall | 0.536（15/28） | 0.464（13/28） | **−0.072** |
| REFUTES Recall | 0.818（18/22） | 0.818（18/22） | **不变** |

混淆矩阵变化（行=真实，列=预测）：

|  | 预测 SUPPORTS | 预测 REFUTES |
|--|--|--|
| 真实 SUPPORTS（n=28） | 无Judge: 15 → 有Judge: **13**（−2） | 无Judge: 13 → 有Judge: **15**（+2） |
| 真实 REFUTES（n=22） | 无Judge: 4 → 有Judge: **4**（不变） | 无Judge: 18 → 有Judge: **18**（不变） |

### 7.4 失败原因分析

**（1）Judge 未纠正任何 REFUTES 误判**

REFUTES→SUPPORTS 误判数在两组中完全相同（均为 4 条），说明二次核验**没有救回任何被误判为 REFUTES 的 SUPPORTS 样本**，其设计目标完全未达成。

**（2）Judge 额外引入了 SUPPORTS 误判**

SUPPORTS→REFUTES 误判从 13 条增加到 15 条，Judge 不仅没有修正错误，反而把 2 个原本正确的 SUPPORTS 翻成了 REFUTES。

**（3）根本原因：残缺证据 + 二分类 = 偏向 REFUTES**

`"Correct the verdict only if the evidence clearly contradicts it"` 在理论上保守，但当 IRCoT 检索到的证据残缺时，Judge 面对的是：初判为 SUPPORTS，而证据无法直接确认 claim 的关键子句。LLM 容易将"无法确认"解读为"证据间接反驳"，从而认为满足了"clearly contradicts"条件，将 SUPPORTS 翻成 REFUTES。

这与尝试四的失败原因高度一致：**检索层失效时，任何判断层的规则都会放大同侧误差**。REFUTES 召回本来已达 0.818（基础核验 prompt 偏保守），再叠加一层同方向的 Judge，相当于对 SUPPORTS 类施加双重偏压。

**（4）API 调用成本加倍，收益为负**

每条 claim 额外多一次 LLM 调用（50 条样本多消耗 50 次），准确率反而下降 4%，性价比极差。

### 7.5 总结

在当前检索质量下，LLM Judge 二次核验是**净负收益**的：既不修复 REFUTES 误判，又额外引入 SUPPORTS 误判，且成本加倍。二次核验思路本身不存在逻辑问题，但其有效性高度依赖证据质量——当证据能可靠覆盖声明的关键子句时，独立视角审核才有意义。

**最终决定：`USE_LLM_JUDGE` 默认值固定为 `False`，不纳入消融实验推荐组合。** 相关代码（`build_judge_review_prompt`）保留在 `src/prompt_builder.py` 中，供后续复现。

## 八、总结

### 8.1 当前最佳实现

**配置**：`USE_MULTI_HOP=True, MAX_HOP_ROUNDS=3, USE_CROSS_ENCODER=True, USE_LLM_JUDGE=False, RETRIEVAL_MODE="BM25"`

**在 seed=42，n=50 基准下：**

| 指标 | 值 |
|------|-----|
| Accuracy | **66%** |
| Macro F1 | **0.657** |
| SUPPORTS Precision / Recall / F1 | 0.824 / 0.500 / 0.622 |
| REFUTES Precision / Recall / F1 | 0.576 / 0.864 / 0.691 |

### 8.2 主要优势

1. **架构可复现**：本地 dump 检索，无网络依赖，同 seed 结果稳定
2. **链式推理有效**：IRCoT 将 HoVer 多跳声明的准确率从 50% 提升至 66%，SUPPORTS 召回从 32% 提升至 50%
3. **可解释性强**：每条 claim 的 `hop_trace` 记录完整推理链（每跳的 Thought、Search 词条、检索结果），便于错误诊断
4. **模块化设计**：各开关独立可控，任意组合均可运行，便于消融实验复现

### 8.3 主要缺陷

| 缺陷类型 | 具体表现 | 影响范围 |
|---------|---------|---------|
| BM25 实体消歧失败 | 同名词条（Street Dogs、Sugar & Spice）命中错误文章，三跳全返回无关内容 | 约 10~15% 的 claim |
| BM25 词汇缺口 | IRCoT 生成的查询词与 Wikipedia 词条标题用词不匹配时得分为零 | 约 5~10% 的 claim |
| LLM "部分支持→整体认可" | 证据确认了部分子句，LLM 忽略其他子句的矛盾（Celtic FC 案例） | 少量但典型 |
| 强制二分类偏向 | 无 NEI 选项，证据不足时 LLM 倾向 REFUTES，SUPPORTS 召回率始终低于 REFUTES | 系统性，贯穿全局 |

### 8.4 可改进方向

1. **提升 BM25 消歧能力**：在 IRCoT 的 hop prompt 中加入更多上下文约束（如 claim 的其他实体名）引导 LLM 生成更精确的查询词，降低同名歧义概率。

2. **改进文档级 Dense 编码**：用段落级而非全文级编码解决 256 token 截断问题；或使用支持长文本的编码模型（如 BGE-M3、E5-large）替代 all-MiniLM-L6-v2，有望在命名实体查询上达到与 BM25 相当的精度，从而真正补充 BM25 的词汇缺口。

3. **引入 NOT ENOUGH INFO 选项**：允许 LLM 在证据不足时输出"不确定"，随后用规则将 NEI 映射到保守判断，可缓解强制二分类的系统性 REFUTES 偏向。

4. **逐子句验证与检索联动**：尝试四表明，逐子句验证需要与检索联动——对每个子句单独触发一次检索，确保证据覆盖每个子句，而非整体检索完后再做逐句分析。代价是 LLM 调用次数显著增加。
