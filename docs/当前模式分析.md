# FEVER 事实验证系统 — 当前模式分析

## 总体架构

```
main.py
  └─ FactVerifier.verify_claims()         逐条遍历
       └─ _verify_single_claim()          按 EXPERIMENT_MODE 分支
            ├─ 检索（可选）               retriever.py / golden_evidence.py
            ├─ 构造 Prompt                prompt_builder.py
            ├─ 调用 LLM API              api_client.py
            └─ 解析响应                  parse_model_response()
  └─ calculate_metrics()                  evaluator.py，多轮聚合后输出
```

数据集固定用 `RANDOM_SEED` 采样一次，所有轮次共用，`NUM_ROUNDS` 次重复推理后取均值 ± 标准差，用于衡量 LLM 输出随机性的影响。

## 各模式详细说明

### 1. BASELINE

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `shared_task_dev.jsonl`（三分类）|
| 检索 | 无 |
| 证据来源 | 纯 LLM 内置知识 |
| Prompt | `build_verification_prompt`：一句话事实 + Final Label |
| LLM 调用次数 | 每条 claim **1 次** |

**预期效果**：作为基准线，评估 LLM 自身知识在 FEVER 上的表现。对于训练数据覆盖的常识类 claim 准确率尚可，对于需要精确数字、日期、冷门事实的 claim 容易出错。NEI（信息不足）类样本大概率被错判为 SUPPORTS/REFUTES，幻觉率最高。

---

### 2. COT（Chain-of-Thought）

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `shared_task_dev.jsonl`（三分类）|
| 检索 | 无 |
| 证据来源 | 纯 LLM 内置知识 |
| Prompt | `build_cot_prompt`：强制分步列举逻辑链条，禁用 Markdown 加粗 |
| LLM 调用次数 | 每条 claim **1 次** |

**预期效果**：思维链迫使模型逐步推理，对逻辑关系复杂或多实体 claim 有改善，但知识来源与 BASELINE 相同。对于模型内置知识本就不足的 claim，CoT 只是更详细地出错，效果未必优于 BASELINE。

---

### 3. RAG（实时 Wikipedia API 检索）

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `shared_task_dev.jsonl`（三分类）|
| 检索 | 实时 Wikipedia API（`wikipedia.search` + `wikipedia.summary`）|
| 证据来源 | Wikipedia 摘要段落 |
| Prompt | `build_rag_prompt`：基于证据做简短对比 + Final Label |
| LLM 调用次数 | 每条 claim **2 次**（关键词提取 1 次 + 验证 1 次）|

**关键词提取步骤**：先调用 LLM 从 claim 中提取 1-2 个核心关键词，用于 Wikipedia 搜索（`wikipedia.search()` 是全文搜索引擎，短关键词效果更好）。若模型返回超过 6 个词，则回退到原始 claim 作为查询词。

**预期效果**：引入外部知识后能处理 LLM 训练截止后的事实，或训练数据覆盖不足的长尾知识。但实时 API 受网络影响大（需代理），且 Wikipedia 摘要可能不包含精确证据句，证据质量不稳定。

---

### 4. RAG_COT（实时检索 + 思维链）

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `shared_task_dev.jsonl`（三分类）|
| 检索 | 实时 Wikipedia API（与 RAG 相同）|
| 证据来源 | Wikipedia 摘要段落 |
| Prompt | `build_rag_cot_prompt`：基于证据做多步推理 + Final Label |
| LLM 调用次数 | 每条 claim **2 次** |

**预期效果**：结合外部知识与多步推理，理论上是最强的在线模式。但 token 消耗最多，API 费用最高，且推理步骤越多解析出错的概率也越高（模型可能在 Analysis 区块里先写出标签，干扰 `parse_model_response` 正则匹配）。

---

### 5. RAG_BM25（本地两阶段检索）

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `shared_task_dev.jsonl`（三分类）|
| 检索 | 本地 wiki-pages dump 两阶段检索 |
| 证据来源 | 本地 `data/wiki-pages/wiki-*.jsonl` |
| Prompt | `build_rag_prompt`（与 RAG 相同）|
| LLM 调用次数 | 每条 claim **1 次**（无关键词提取步骤）|

**两阶段检索流程**：

```
claim 全文
  └─ 第一阶段：BM25 文档检索
       从索引中召回 Top-N 篇文档（默认 N=5）
  └─ 第二阶段：Sentence-BERT 句子排序
       从召回文档中取所有句子（每篇最多 MAX_SENTENCES_PER_DOC=50 句）
       用余弦相似度排序，保留 Top-K 句（默认 K=5）
  └─ 格式化输出：[1] (Page Title, 句#id) 句子文本
```

**为什么不提取关键词**：BM25 对完整 claim 的检索效果优于 1-2 个关键词，IDF 加权会自然压低停用词权重、抬高实体词权重，无需预先过滤。而 Wikipedia API 是全文搜索引擎，短关键词更合适，两者场景不同。

**首次运行需要**：扫描 `data/wiki-pages/` 构建 BM25 索引（过滤模式只索引 dev 集 evidence 涉及的页面，约数万篇，耗时 5-15 分钟），持久化到 `data/bm25_index/`，后续直接加载复用。

**预期效果**：完全离线，不依赖网络和代理；检索到的是 FEVER 数据集对应的原始 Wikipedia dump，与 ground-truth 证据来源一致；但 BM25 是词频匹配，对语义相近但词汇不重叠的 claim 召回率有限。

---

### 6. RAG_GOLDEN（Gold Evidence 上界）

| 项目 | 内容 |
|------|------|
| 数据集 | FEVER `train.jsonl`（含 evidence 坐标标注，三分类）|
| 检索 | 无检索，直接按坐标取句 |
| 证据来源 | FEVER 标注的 `(wikipedia_page, sentence_id)` → 本地 dump 原句 |
| Prompt | `build_rag_prompt`（与 RAG、RAG_BM25 相同）|
| LLM 调用次数 | 每条 claim **1 次** |

**证据解析流程**：

```
train.jsonl
  └─ 解析 evidence 字段 → [(page, sentence_id), ...]
  └─ 扫描 data/wiki-pages/wiki-*.jsonl
       按 doc_id 匹配 → 按 sentence_id 取原句
  └─ 缓存到 data/cache/golden_evidence_sentences.json（避免重复扫描）
  └─ 拼接为 [1] (Page, 句#id) 句子 格式
```

**预期效果**：证据是 FEVER 标注的 ground-truth 原句，质量最高、噪声最低，代表"检索增强"的理论上限（Oracle RAG）。该模式的准确率衡量的是：**当证据完美时，LLM 的推理能力能达到多高**，而非检索系统的能力。与其他模式对比，可以量化检索质量损失带来的性能差距。

---

### 7. EXTENDED_PIPELINE（多跳推理）

| 项目 | 内容 |
|------|------|
| 数据集 | HoVer `data/cache/hover_dev.json`（**二分类**：SUPPORTS / REFUTES）|
| 检索 | 实时 Wikipedia API，多页面检索 + SBERT 句子筛选 |
| 证据来源 | 多篇 Wikipedia 页面的合并句子集合 |
| Prompt | `build_llm_judge_prompt`（LLM-as-Judge 格式）|
| LLM 调用次数 | 每条 claim **2 次**（关键词提取 + 验证）|

**与其他模式的关键区别**：
- 使用 HoVer 数据集，claim 需要跨多个 Wikipedia 页面才能验证（多跳推理），FEVER 单跳 claim 不适用
- 标签只有两类（HoVer 无 NOT ENOUGH INFO），幻觉率指标无意义
- Prompt 采用 LLM-as-Judge 风格，比 `build_rag_prompt` 更偏向"法官裁决"语气

**预期效果**：测试系统处理需要多步证据链接的复杂 claim 的能力，但实时 API 网络依赖和多跳信息整合是主要瓶颈。

## 模式横向对比

| 模式 | 数据集 | 检索方式 | 证据质量 | 网络依赖 | LLM 调用/条 |
|------|--------|----------|----------|----------|-------------|
| BASELINE | FEVER dev | 无 | — | 否 | 1 |
| COT | FEVER dev | 无 | — | 否 | 1 |
| RAG | FEVER dev | 实时 Wikipedia API | 低~中 | **是** | 2 |
| RAG_COT | FEVER dev | 实时 Wikipedia API | 低~中 | **是** | 2 |
| RAG_BM25 | FEVER dev | 本地 BM25 + SBERT | 中 | 否 | 1 |
| RAG_GOLDEN | FEVER train | 无（按坐标取句）| **最高（Oracle）** | 否 | 1 |
| EXTENDED_PIPELINE | HoVer dev | 实时 Wikipedia API | 中 | **是** | 2 |

## 评估指标说明

所有模式共用同一套评估体系（`evaluator.py`）：

| 指标 | 说明 |
|------|------|
| Accuracy | 整体准确率 |
| Macro Precision / Recall / F1 | 三类标签不加权平均，对类别不均衡敏感 |
| Weighted Precision / Recall / F1 | 按样本数加权，反映整体性能 |
| **Hallucination Rate（幻觉率）** | 真实标签为 NOT ENOUGH INFO、但预测为 SUPPORTS 或 REFUTES 的比例；越低越好 |
| 混淆矩阵 | 3×3，行为真实标签，列为预测标签 |

> 幻觉率是该系统最重要的业务指标：模型将"证据不足"的 claim 强行判断为支持或反驳，在事实核查场景中危害最大。
